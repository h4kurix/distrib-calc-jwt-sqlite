# Распределённый вычислитель арифметических выражений

Сервис принимает арифметическое выражение, разбивает его на атомарные задачи
и распределяет их между агентами. Оркестратор хранит состояние в SQLite.
Агенты забирают задачи из общего пула по внутреннему API и возвращают результат.

## Возможности

- операции `+`, `-`, `*`, `/`, скобки и унарный знак.
- JWT для пользователей и отдельные токены агентов.
- параллельная работа агентов с одним пулом задач.
- SQLite в режиме WAL.
- веб-интерфейс и Docker Compose.

## Быстрый старт

```bash
git clone https://github.com/h4kurix/distrib-calc-jwt-sqlite
cd distrib-calc-jwt-sqlite
cp .env.example .env
```

Задайте в `.env` свои `JWT_SECRET` и `AGENT_BOOTSTRAP_KEY`. Сервис откажется
стартовать со значениями из примера.

```bash
docker compose up --build
```

Откройте `http://localhost:8080`.

### Масштабирование

`deploy.replicas` без Swarm не работает. Число агентов задаётся при запуске:

```bash
docker compose up --build --scale agent=8
```

`COMPUTING_POWER` задаёт число воркеров внутри одного контейнера агента.
Общее число параллельных задач — агенты × воркеры.

## Конфигурация

Все параметры читаются из окружения.

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `JWT_SECRET` | ключ подписи JWT, обязателен | — |
| `AGENT_BOOTSTRAP_KEY` | ключ выдачи токенов агентов, обязателен | — |
| `ENV`, `LOG_LEVEL` | окружение и уровень логов | `dev`, `info` |
| `PORT` | порт оркестратора | `8080` |
| `ORCHESTRATOR_HOST`, `ORCHESTRATOR_PORT` | адрес оркестратора для агента | `localhost`, `8080` |
| `DB_PATH` | путь к SQLite | `data/calculator.db` |
| `COMPUTING_POWER` | воркеров в контейнере агента | `16` |
| `MAX_EXPRESSION_LEN`, `MAX_TASKS_PER_EXPR` | лимиты сложности выражения | `256` |
| `MAX_OPERATION_TIME_MS` | потолок времени операции | `30000` |
| `TIME_ADDITION_MS`, `TIME_SUBTRACTION_MS`, `TIME_MULTIPLICATIONS_MS`, `TIME_DIVISIONS_MS` | искусственная пауза операции, `0` отключает | `0` |
| `AGENT_TOKEN_TTL`, `USER_TOKEN_TTL` | срок жизни токенов | `24h` |
| `STALE_TASK_TIMEOUT` | когда задача возвращается в очередь | `2m` |
| `EXPRESSION_TIMEOUT` | когда выражение закрывается по таймауту | `10m` |
| `TASK_POLL_INTERVAL` | интервал опроса очереди агентом | `500ms` |
| `REQUEST_TIMEOUT`, `MAX_RETRIES`, `RETRY_BASE_DELAY` | HTTP-клиент агента и ретраи | `10s`, `5`, `2s` |
| `STATIC_DIR` | каталог статики оркестратора | `./static` |

Роуты `register` и `login` ограничены: 20 запросов с адреса в минуту.
При превышении сервер отвечает `429` с JSON.

## API

Базовый путь: `/api/v1`. Все ошибки — JSON вида `{"error":"..."}`.

### Регистрация и вход

```bash
curl -X POST http://localhost:8080/api/v1/register \
  -H "Content-Type: application/json" \
  -d '{"username":"test","password":"password123"}'

curl -X POST http://localhost:8080/api/v1/login \
  -H "Content-Type: application/json" \
  -d '{"username":"test","password":"password123"}'
```

Ответ: `{"token":"..."}`.

### Вычисление и статус

```bash
curl -X POST http://localhost:8080/api/v1/calculate \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <token>" \
  -d '{"expression":"2+3*4"}'

curl http://localhost:8080/api/v1/expressions/<id> \
  -H "Authorization: Bearer <token>"
```

Ответ на создание: `{"id":"expr-..."}`. Статусы: `pending`, `in_progress`,
`completed`, `error`. Ошибка вычисления приходит в поле `error`.
Пользователь видит только свои выражения.

### Список выражений

```bash
curl http://localhost:8080/api/v1/expressions \
  -H "Authorization: Bearer <token>"
```

## Архитектура

- `cmd/orchestrator` — HTTP API, выдача задач, обслуживание очереди.
- `cmd/agent` — воркеры, получение задач и отправка результатов.
- `internal/calculator` — валидация, парсер, дерево выражения, агрегация.
- `internal/store` — доступ к SQLite, атомарный захват задач.
- `internal/handler` — HTTP-слой, JWT, проверка владельца, rate limit.
- `internal/config`, `internal/database`, `internal/logger`, `internal/id` —
  внутренние служебные пакеты.

Задача захватывается в транзакции со статусом `claimed`. Два агента не получат
одну и ту же задачу. Готовность задачи определяется по таблице
`task_dependencies`. Финализация выражения идёт в обработчике результата,
в одной транзакции. Зависшие задачи возвращаются в очередь по
`STALE_TASK_TIMEOUT`.

### Ограничения

- длина выражения — до 256 символов.
- число задач — до 256 на выражение.
- выражение без операций отклоняется с `422`.

## Бенчмарки

Замеры на локальной машине: Windows, Go 1.26, SQLite WAL, драйвер
`modernc.org/sqlite`. Если не указано иначе, искусственные паузы операций
отключены (`TIME_*=0`).

### Парсинг

| Что | Время |
|---|---:|
| `POST /calculate`, 99 операций и 99 задач | 3–9 мс |

Парсер и планировщик не являются узким местом.

### Параллелизм

Выражение — сбалансированное дерево из 63 независимых операций, 251 символ,
результат `64`. Пауза каждой операции — 100 мс.

| Воркеров | Время |
|---:|---:|
| 1 | 6.56 с |
| 2 | 3.56 с |
| 4 | 2.09 с |
| 8 | 1.26 с |
| 16 | 0.88 с |

Ускорение — 7.4 раза. Нижняя граница задана глубиной дерева: 6 уровней ×
100 мс = 0.6 с. Остальное — сетевые вызовы и работа с БД.

### Сложные выражения без пауз

| Выражение | Операций | Время | Результат |
|---|---:|---:|---:|
| сбалансированное дерево, 251 символ | 63 | 0.11–0.20 с | `64` |
| `-1+-1+...`, 254 символа | 169 | 0.40 с | `-85` |
| 255 минусов подряд, 256 символов | 255 | 0.71 с | `-1` |

Цепочка из 255 операций не распараллеливается по смыслу: каждая следующая
задача зависит от предыдущей.

### Общий пул

Четыре отдельных процесса агента, по 4 воркера в каждом. Одновременно
отправлены 20 выражений по 63 операции.

```text
задач:              1260
время:              1.8 с
результат 64:       20 из 20
уникальных захватов: 1260 из 1260
SQLITE_BUSY:        0
ошибок:             0
```

### Устойчивость

- Падение агента после захвата задачи: с `STALE_TASK_TIMEOUT=3s` выражение
  завершилось за 4 с, задача вернулась в очередь.
- Нагрузка 62 с, 104 выражения: память оркестратора 23.5 → 29.9 МБ,
  агентов 15 → 17.5 МБ. Рост остановился. `SQLITE_BUSY=0`, паник нет.
- Старая база без колонок `status`, `attempts`, `error`, `claimed_at`
  открывается и мигрируется при старте.

### Как повторить

Установите в `.env`: `TIME_*=0`, `COMPUTING_POWER=16`.
Запуск: `docker compose up --build --scale agent=4`.
Сбалансированное выражение получают повторным вложением:
`x = "1+1"`, затем пять раз `x = "(" + x + ")+(" + x + ")"`.
Отправьте `POST /api/v1/calculate` и опрашивайте статус до `completed`.

## Переиспользование: фоновый обработчик задач

Арифметика здесь — пример. Тот же каркас подходит для фоновых задач.
Например: отправка webhook, ресайз изображений, генерация PDF, вызов ML-модели.

Ядро уже решает то, что обычно пишут с нуля.

- Приём задачи по HTTP и возврат идентификатора.
- Хранение состояния и результата в SQLite.
- Раздача задач нескольким агентам без дублей.
- Повтор неудачных шагов и возврат зависших задач в очередь.
- Проверка владельца и прав агента через JWT.
- Страница со статусом задачи.

### Что заменить

1. `internal/calculator` → `internal/jobs`. Вместо парсера нужен реестр
   обработчиков. Ключ — тип задачи, значение — функция.
2. `store.Task`. Поля `arg1`, `arg2`, `operator` заменить на `type`
   и `payload` с JSON. Статусы и `task_dependencies` оставить.
3. Агент. Вместо `calculate(op, arg1, arg2)` вызывать обработчик по типу.
4. API. `POST /api/v1/calculate` → `POST /api/v1/jobs` с телом
   `{"type":"webhook","payload":{"url":"..."}}`.

### Что добавить

- Раздельные очереди или приоритеты, чтобы тяжёлые задачи не блокировали
  лёгкие.
- Ограничение числа попыток и задержку между ними.
- Метрики: длина очереди, время выполнения, число ошибок.
- Результат в JSON вместо одного числа.

### Первый шаг

Взять тип `webhook`. Обработчик делает HTTP POST по адресу из `payload`
и сохраняет код ответа. Проверить на том же сценарии: создать задачу,
дождаться `completed` и видеть, что два агента не получили её дважды.

go test ./... -count=1
